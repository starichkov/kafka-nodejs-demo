# Kafka glossary

This glossary defines the Kafka terms used throughout the demo. Each definition points to a concrete setting, source module, or lesson so the vocabulary can be connected to an observable experiment.

## Core Kafka concepts

| Term                 | Meaning in Kafka                                                                                                                                                                                      | Where to see it in this demo                                                                                             |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| **Broker**           | A Kafka server that accepts records from producers, stores them, and serves them to consumers. A Kafka cluster normally contains multiple brokers; this demo runs one broker to keep the setup small. | The `kafka` service in `docker-compose.yml`; [architecture](architecture.md)                                             |
| **Bootstrap server** | An address a client uses to make its first connection. The broker returns cluster metadata after that connection, so the address is not necessarily the endpoint used for every request.              | `KAFKA_BROKERS` in `README.md`; `localhost:9092` for host processes and `kafka:9092` for Compose services                |
| **Cluster**          | A group of Kafka brokers that share metadata and distribute topic partitions. A cluster can continue operating when individual brokers fail if it has enough replicas.                                | This learning setup is a single-broker cluster and is not fault tolerant.                                                |
| **KRaft**            | Kafka's current metadata-management mode, where Kafka uses its own controllers instead of requiring a separate ZooKeeper service.                                                                     | `KAFKA_PROCESS_ROLES` and `KAFKA_CONTROLLER_QUORUM_VOTERS` in `docker-compose.yml`                                       |
| **Controller**       | The Kafka process role responsible for cluster metadata and coordination, including broker and partition state. In this demo the same process is both broker and controller.                          | `KAFKA_PROCESS_ROLES: broker,controller` in `docker-compose.yml`                                                         |
| **Topic**            | A named stream of records. Producers write to a topic and consumers read from it. A topic is split into one or more partitions.                                                                       | The default topic is `demo-topic`; [Lesson 1](lesson-01-basics.md) follows one record through it.                        |
| **Partition**        | An ordered, append-only sequence inside a topic. Kafka assigns each record a numeric partition and an offset within that partition.                                                                   | `PARTITION_COUNT` and `PARTITION` in `README.md`; [Lesson 3](lesson-03-partitions-and-ordering.md)                       |
| **Offset**           | The position of a record within one partition. Offsets are scoped to a partition, so offset `5` in partition `0` is different from offset `5` in partition `1`.                                       | Producer and consumer logs; `npm run inspect:topic`; [Lesson 4](lesson-04-headers-timestamps-and-inspection.md)          |
| **Retention**        | The policy that determines how long Kafka keeps records. Records remain available according to retention settings even after a consumer reads them.                                                   | The local demo uses disposable broker data; retention is a broker/topic concern rather than a consumer delete operation. |
| **Record**           | Kafka's unit of data: a value plus optional key, headers, timestamp, topic, partition, and offset metadata. Kafka stores the key, value, and headers as bytes.                                        | `produceMessage()` in `src/producer.js` and `processMessage()` in `src/consumer.js`                                      |

## Producing records

| Term                        | Meaning in Kafka                                                                                                                                                                                                 | Where to see it in this demo                                                                                                                                 |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Producer**                | A client that publishes records to Kafka. It chooses a topic and can provide a key or partition; Kafka returns delivery metadata after accepting the record.                                                     | `src/producer.js`; `npm run start:producer`                                                                                                                  |
| **Key**                     | Optional record data used by the partitioner. With the default partitioner, records with the same key are normally routed to the same partition, preserving their order relative to one another.                 | `KEY` in `README.md`; the same-key experiment in [Lesson 3](lesson-03-partitions-and-ordering.md)                                                            |
| **Partitioner**             | The producer component that selects a partition for a record when no explicit partition is supplied. The selection can use the key and available partition metadata.                                             | `Partitioners.DefaultPartitioner` in `src/producer.js`                                                                                                       |
| **Timestamp**               | A millisecond timestamp associated with a record. It can be supplied by the producer or assigned by Kafka, depending on the topic's timestamp configuration.                                                     | `MESSAGE_TIMESTAMP` and consumer output; [Lesson 4](lesson-04-headers-timestamps-and-inspection.md)                                                          |
| **Header**                  | Optional key/value metadata attached to a record. Headers are useful for tracing or routing hints without changing the main payload. They do not replace a schema for the value.                                 | `MESSAGE_HEADERS`, `normalizeHeaders()`, and the `trace-id` example in Lesson 4                                                                              |
| **Acknowledgment (`acks`)** | The producer setting that controls how much broker confirmation is required before a send is considered successful. `0` requires no response, `1` waits for the leader, and `-1` waits for all in-sync replicas. | `PRODUCER_ACKS` and [Lesson 6](lesson-06-acknowledgments-retries-and-idempotence.md); this single-broker demo cannot demonstrate replica failure guarantees. |
| **Producer retry**          | A Kafka client retry of a failed network or protocol request. Retries can improve resilience but may create duplicates when the result of an earlier request is unknown.                                         | `PRODUCER_RETRIES` in `src/producer.js`; distinct from consumer application retries in [Lesson 5](lesson-05-failures-retries-and-dead-letters.md)            |
| **Idempotent producer**     | A producer mode that helps Kafka avoid duplicate writes caused by producer retries, within Kafka's supported delivery semantics. It is not the same as an end-to-end exactly-once business workflow.             | `PRODUCER_IDEMPOTENT` and [Lesson 6](lesson-06-acknowledgments-retries-and-idempotence.md)                                                                   |

## Consuming records

| Term                         | Meaning in Kafka                                                                                                                                                                                                                | Where to see it in this demo                                                                                       |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| **Consumer**                 | A client that fetches records from Kafka and passes them to application code. It tracks progress through offsets rather than removing records from the topic.                                                                   | `src/consumer.js`; `npm run start:consumer`                                                                        |
| **Consumer group**           | A set of consumers cooperating under one group ID. Kafka assigns each partition to at most one active member of the group, allowing work to be shared.                                                                          | `KAFKA_GROUP_ID`; [Lesson 2](lesson-02-groups-and-offsets.md) and [Lesson 3](lesson-03-partitions-and-ordering.md) |
| **Group coordinator**        | The broker responsible for managing a consumer group's membership, partition assignments, and committed offsets.                                                                                                                | KafkaJS logs during group startup/rebalancing; the consumer's `groupId` configuration                              |
| **Rebalance**                | The reassignment of partitions when group membership or topic partitions change. During a rebalance, ownership can move between consumers and delivery may briefly pause.                                                       | Start two consumers with the same group ID in Lesson 3.                                                            |
| **Committed offset**         | A consumer group's durable checkpoint for a partition. On restart, the group normally resumes from its committed position rather than automatically replaying everything.                                                       | `FROM_BEGINNING` behavior in [Lesson 2](lesson-02-groups-and-offsets.md)                                           |
| **`fromBeginning`**          | A consumer subscription option used when the group has no committed offset for a partition. It selects the earliest available record instead of the latest position; it is not a rewind command for an already committed group. | `FROM_BEGINNING` in `src/consumer.js` and Lesson 2                                                                 |
| **At-least-once processing** | A common consumer outcome where a record may be delivered again if processing fails before its progress is committed. Handlers should therefore tolerate duplicates when needed.                                                | Retry and failure behavior in [Lesson 5](lesson-05-failures-retries-and-dead-letters.md)                           |
| **Application retry**        | A retry performed by the message handler after it has received a record. It is different from KafkaJS retrying a network request.                                                                                               | `MAX_RETRIES` and `RETRY_BACKOFF_MS` in `src/consumer.js`                                                          |
| **Dead-letter topic (DLQ)**  | A separate topic where an application publishes records that could not be processed after its retry policy. A DLQ is an application convention, not a special Kafka topic type.                                                 | `DEAD_LETTER_TOPIC` and Lesson 5                                                                                   |

## Client and deployment terms

| Term                    | Meaning in Kafka                                                                                                                                                                         | Where to see it in this demo                                                                                          |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| **Client ID**           | A name identifying a producer, consumer, or admin client in broker logs and metrics. It is not a consumer group identity.                                                                | `KAFKA_CLIENT_ID` in the configuration defaults                                                                       |
| **Admin client**        | A Kafka client used for cluster and topic operations rather than normal record production or consumption.                                                                                | `inspectTopic()` in `src/topic-admin.js` fetches partition offset ranges.                                             |
| **Topic metadata**      | Information Kafka returns about a topic, such as its partitions and leaders. Clients use it to route requests correctly.                                                                 | `waitForKafkaConnectivity()` checks broker metadata; `inspect:topic` reports partition ranges.                        |
| **Advertised listener** | The address a broker tells clients to use after the initial connection. It must be reachable from the client's network, which is why Compose uses separate host and container addresses. | `KAFKA_ADVERTISED_LISTENERS` in `docker-compose.yml`; [architecture](architecture.md)                                 |
| **Internal listener**   | A broker listener intended for clients on the Docker or private network.                                                                                                                 | `INTERNAL://kafka:9092` in Compose                                                                                    |
| **External listener**   | A broker listener published for clients outside the Docker network.                                                                                                                      | `EXTERNAL://localhost:9092` and port mapping in Compose                                                               |
| **Replication factor**  | The number of broker copies maintained for a topic or internal Kafka topic. Higher replication improves fault tolerance when enough brokers are available.                               | Topic setup uses replication factor `1`; `KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR=1` reflects the single-broker setup. |
